# NL2SQL 语义层 —— 企业生产就绪度评估

> 版本：v1（2026-08-30）｜范围：feature/nl2sql-semantic-layer 全部能力
> 结论先行：**架构方向正确、核心算法已验证，但距离企业生产级还差一批"工程化/治理/合规"硬骨头——当前就绪度约 40%。**
> 差距集中在四类：① 无真实评测证明 ② 无鉴权/权限/审计 ③ 无运维基线（健康检查/监控/配置/部署）④ 无 API 层测试与错误模型。

---

## 1. 总评

| 维度 | 就绪度 | 一句话 |
|---|---|---|
| 核心算法 | ★★★★☆ | PPR 语义链接 + P0/P2/BM25/意图/黑话，压测 R@5 0.91 / MRR 0.544 |
| 数据持久化 | ★★★☆☆ | 灌图→读图链路通、幂等，但无版本/增量调度/质量校验 |
| 工程健壮性 | ★★☆☆☆ | 无鉴权、无 healthz、无超时矩阵、错误模型不统一 |
| 性能与规模 | ★★☆☆☆ | 只验到 73 列合成语料；真实几百表未基准，索引首查懒构建 |
| 安全合规 | ★☆☆☆☆ | 无数仓表级权限、无审计、无脱敏（敏感字段风险） |
| 可运维性 | ★☆☆☆☆ | 无部署产物、无监控、无 CI、无运维手册 |
| 测试覆盖 | ★★☆☆☆ | 单元 257 过，但 **API 层 0 测试**、无端到端、无真实评测集 |
| **综合** | **~40%** | 算法验证充分，工程化/治理/合规是主缺口 |

## 2. 分维度差距（现状 → 生产要求）

### 2.1 评测与质量证明（★ 最大差距）
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| 真实评测集 | 23 题合成语料（9 题人为对抗题） | 真实 schema + 50-100 真实问题 + 人工标注 gold | **P0** |
| 准确率基线 | 只有检索指标（R@/MRR） | 端到端 answer-level 准确率（对标他们 78%） | **P0** |
| golden SQL 集 | 无 | 标注正确 SQL，校验生成质量 | P1 |
| 回归门禁 | 手动跑 | 每次改动自动回归（评测集 + 257 单测接 CI） | P1 |

### 2.2 安全与合规（★ 企业最硬门槛）
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| 鉴权 | 挂在共享 api_auth router，**未验证实际强度** | 明确 token/内部服务鉴权，禁用匿名 | **P0** |
| 表级权限 | 无 | 数仓敏感表/字段（手机号、身份证）访问控制——**谁能查哪个库** | **P0** |
| 审计日志 | 无 | 谁、何时、问了什么、返回什么 | **P0** |
| 脱敏 | 无 | 敏感字段结果脱敏 | P1 |
| SQL 注入面 | validator 只读校验，风险低 | 执行器上线时限定只读+库白名单 | P1 |

### 2.3 工程健壮性
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| healthz/就绪探针 | **确认缺失** | /healthz + 依赖（图/向量/LLM）状态 | **P0** |
| 优雅降级矩阵 | embedding 挂了→lexical ✓；图挂了/向量挂了/LLM 挂了未定义 | 每依赖一张降级表（降级 or 503） | **P0** |
| 错误模型 | HTTPException 裸抛，无错误码 | 统一错误码 + 可读 message + 平台可编程处理 | **P0** |
| 超时/重试 | run 端点直接调 LLM 无超时 | LLM/向量/图调用超时 + 重试 + 熔断 | **P0** |
| 配置化 | Base URL/top_k/阈值散在 env/硬编码 | 集中配置（config 文件 + env 模板） | P1 |
| 请求串联 | 无 request-id | 日志按 request-id 串联，便于排障 | P1 |

### 2.4 性能与规模
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| 规模基准 | 12 表/73 列 | 几百-几千表、十万级列：延迟 p50/p99、QPS 基准 | **P0** |
| PPR 开销 | LocalEngine networkx 每问全图迭代 | 大图切 Vermeer（已实现未真实规模验证） | P1 |
| 索引构建 | 向量/BM25 **首查懒构建**（首问卡顿） | 加载时预构建 / 后台预热 | **P0** |
| 向量库 | numpy 内存 / Milvus·OceanBase 未真连 | 生产向量持久化 + 连接验证 | P1 |

### 2.5 数据治理
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| 元数据质量校验 | 无（重复表/列、空 comment、口径冲突无告警） | 灌入前校验 + 告警 | **P0** |
| schema 版本管理 | 无 | 图变更 diff/回滚/快照 | P1 |
| 增量同步 | PRIMARY_KEY 幂等，但无触发/调度 | 元数据变更自动增量同步（事件/定时） | P1 |
| 血缘完整性 | loader 只读不校验 | 血缘闭环校验（表在血缘中可达） | P2 |

### 2.6 可运维性
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| 部署产物 | 无（Dockerfile/helm/systemd） | 容器化 + 环境分离（dev/staging/prod） | P1 |
| 监控 | 无 prometheus 指标 | QPS/延迟/命中率/out_of_kb 率/降级计数 | P1 |
| CI | 无 | 单测+冒烟+压测接流水线 | P1 |
| 运维手册 | 无 | 部署/日志/恢复/图挂了怎么办 | P1 |

### 2.7 测试覆盖
| 项 | 现状 | 生产要求 | 优先级 |
|---|---|---|---|
| 单元 | 257 通过 ✓ | 保持 | - |
| **API 层** | **0 个 nl2sql_api 测试** | 7 端点请求/响应/降级/拒答用例 | **P0** |
| 端到端 | e2e 灌图读图 ✓ | 真实链路（灌→读→link→schema_context→run） | P1 |

### 2.8 已知隐藏坑（上线前必排）
- ingest `--clear` 对中文顶点 id 报 ASCII 编码错误（clear 非核心，但要修或禁用提示）
- reload 内存路径仍留在代码（生产已禁用，建议彻底移除或加醒目警告）
- run 端点无 LLM 超时（慢 LLM 挂住请求）
- 首查懒构建向量索引（真实几百表首问会卡数秒-数十秒）

## 3. 整改路线

### P0 —— 上线前必须（进度：5/6 已完成，2026-08-30）
1. ⏳ **真实评测集 + 准确率基线**（唯一未完成，等明天真实数据）
2. ⏳ **鉴权 + 表级权限**（依赖数仓 DBA 权限清单，架构位已预留 api_auth）
3. ✅ **healthz + 降级矩阵**：GET /nl2sql/healthz（engine/embedder/HG 依赖 + degraded 列表；图挂→503 NL2SQL_DEPENDENCY_UNAVAILABLE，embedder 挂→lexical）
4. ✅ **API 层测试 + 错误模型**：统一错误码（NL2SQL_BAD_REQUEST/OUT_OF_KB/LLM_UNAVAILABLE/DEPENDENCY_UNAVAILABLE/TIMEOUT/INTERNAL）+ 11 个 API 契约测试
5. ✅ **索引预构建**：SchemaLinker.prebuild() + pipeline.prebuild()，get_pipeline/load_hugegraph 加载时预热（响应 prebuilt:true）
6. ✅ **元数据质量校验**：/nl2sql/validate + validate_metadata（DUP_TABLE/DUP_COLUMN/COL_NO_COMMENT/COL_ORPHAN/TERM_CONFLICT/BIND_MISSING_COLUMN/FK·LINEAGE_ENDPOINT_MISSING）
   **隐藏坑已排**：ingest clear 改全图 clear API（PRIMARY_KEY id 删不掉问题）；reload 内存端点已移除；run LLM 60s 超时→504

### P1 —— 上线后 1-2 周
7. 规模基准（几百表）+ Vermeer 验证
8. 审计日志 + 配置化 + request-id
9. 超时/重试/熔断（LLM/向量/图）
10. CI + 监控指标 + schema 版本管理
11. 增量同步调度 + 部署产物 + 运维手册

### P2 —— 持续
12. 脱敏 + 字段级权限 + golden SQL + 答案级评估
13. SLO/容量规划 + 多环境隔离

## 4. 建议

**算法层已经到位，明天对接先用真实数据建评测集——这既是验收标准，也是上线闸门。** 评测集建好后，按 P0 清单逐项补齐工程化短板；最优先的是"真实准确率 + 鉴权权限 + healthz/降级"三件套，这三样决定它能不能从 demo 变成平台可依赖的服务。
